# P3.2 deployment and verification

This phase adds three server-side functions:

- `registerReminderRecipient`: called after a user accepts the subscription prompt. It obtains `OPENID` only from `cloud.getWXContext()`, encrypts it with AES-256-GCM, and stores the ciphertext in `notification_recipients`.
- `scheduledReminderScan`: scheduled trigger. It evaluates `reminder_settings` and `items`, creates deterministic records in `reminder_jobs`, and writes safe status summaries to `notification_logs`.
- `sendReminderNotifications`: processes `ready` jobs. It never sends when `REMINDER_DRY_RUN=true`; after dry-run approval it performs the official `cloud.openapi.subscribeMessage.send` call.

## Collections

Create these collections in the active CloudBase environment. Configure permissions so the client cannot read or write them; the cloud functions use them server-side.

- `reminder_jobs`
- `notification_logs`
- `notification_recipients`

`notification_recipients.status` is a server-only lifecycle: `active` (one unused authorization), `sending` (claimed by one job), `consumed` (the one-time authorization was used), `unavailable`, `banned`, or `disabled`. A new user authorization replaces the encrypted recipient value and creates a new `grantVersion` with `status: active`.

Do not create client-facing queries for these collections. They must never contain plaintext `openid`, template responses, keys, image paths, or full error stacks.

## Environment variables

Configure the variables by function. Do not paste the complete list into every function blindly.

`registerReminderRecipient` requires only:

```text
OWNER_KEY_SALT=<the existing server-only value>
REMINDER_RECIPIENT_ENCRYPTION_KEY=<a new random server-only secret>
```

`scheduledReminderScan` requires:

```text
OWNER_KEY_SALT=<the existing server-only value>
REMINDER_DRY_RUN=true
REMINDER_TEMPLATE_ID=<the real template ID from the platform console>
REMINDER_TEMPLATE_FIELDS={"itemName":"thing5","productionDate":"time8","daysLeft":"number2","expiryDate":"date1","note":"thing3"}
REMINDER_TIMEZONE=Asia/Shanghai
REMINDER_MAX_RETRIES=2
```

`sendReminderNotifications` requires:

```text
REMINDER_DRY_RUN=true
REMINDER_TEMPLATE_ID=<the real template ID from the platform console>
REMINDER_TEMPLATE_FIELDS={"itemName":"thing5","productionDate":"time8","daysLeft":"number2","expiryDate":"date1","note":"thing3"}
REMINDER_TIMEZONE=Asia/Shanghai
REMINDER_MAX_RETRIES=2
REMINDER_RECIPIENT_ENCRYPTION_KEY=<the same random server-only secret used by registerReminderRecipient>
REMINDER_MINIPROGRAM_STATE=trial
```

The five field names above are the keys shown in the supplied template screenshot. Confirm the template detail page's exact type, length and display-format limits before switching dry-run off. The value is the API data key without the `.DATA` suffix. The code maps ISO dates to the official Chinese calendar display form for `date`/`time` fields and sends `number` fields as numeric text; adjust only after checking the actual template detail page.

Keep `REMINDER_MINIPROGRAM_STATE=trial` for a developer/experience-account test. Before sending to ordinary users in the formal release, set it to `formal` on `sendReminderNotifications` and deploy again.

Generate the encryption secret locally and do not send it in chat:

```powershell
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

Never put these variables in `env.js`, a page, a Git commit, a database business record, or a log.

### Screenshot/configuration review

The supplied three screenshots have the correct variable separation:

- `registerReminderRecipient`: `OWNER_KEY_SALT` plus `REMINDER_RECIPIENT_ENCRYPTION_KEY` only;
- `scheduledReminderScan`: `OWNER_KEY_SALT` plus scan/template variables, with `REMINDER_DRY_RUN=true`;
- `sendReminderNotifications`: the same recipient encryption key plus template/retry variables, with `REMINDER_DRY_RUN=true`; it does not need `OWNER_KEY_SALT`.

The values shown in the screenshots are nevertheless exposed. Before any real send:

1. Generate a new `REMINDER_RECIPIENT_ENCRYPTION_KEY`, replace it in both `registerReminderRecipient` and `sendReminderNotifications`, deploy both functions, and have the test account authorize again. Existing recipient ciphertext cannot be decrypted with a new key.
2. Treat the displayed `OWNER_KEY_SALT` as compromised. Do not replace it in only one function: it is part of the account-ownership identity used by `login`, `syncData`, `imageProcess`, `logRecognition`, `scheduledReminderScan`, and `registerReminderRecipient`. A salt rotation requires a coordinated migration of owner-scoped records and all six functions. Until that migration is planned and verified, keep the current value unchanged to avoid stranding existing data, and do not copy it into source or chat.
3. The template ID is configuration, not a secret, but the exact template type/length rules still need confirmation in the template detail page. The sender now formats `time`, `date`, `number`, and `thing` fields according to their field prefixes; a test send remains mandatory.

## Deploy order

1. In WeChat Developer Tools, upload and deploy `registerReminderRecipient`, `scheduledReminderScan`, and `sendReminderNotifications` using all files.
2. Create the three collections and apply server-only permissions.
3. Set the environment variables above in the CloudBase console for each function.
4. Re-upload after changing function environment variables if the console requires it.
5. Keep `REMINDER_DRY_RUN=true`.

Set the sender timeout high enough for two database writes and one `subscribeMessage.send` call (10-15 seconds is a practical starting point). The default 3-second timeout visible in the screenshot is suitable for a tiny dry-run but too tight for a real send and can leave a claimed job in `sending`.

## Trigger setup

Create a low-frequency scheduled trigger for `scheduledReminderScan`, for example every 10 minutes. The function itself respects each user's `remindTime` in `Asia/Shanghai` and deterministic dedupe prevents duplicate jobs.

When real sending is approved, create a second low-frequency trigger for `sendReminderNotifications` shortly after the scan trigger, or invoke it from an existing trusted server-side scheduler. Do not call it from a page. Keep the sender disabled while dry-run validation is incomplete.

## Dry-run verification

1. Log in on a test device and accept the subscription prompt. Confirm the page records the preference and that `notification_recipients` contains only encrypted fields.
2. Wait for the scan trigger, or invoke `scheduledReminderScan` from the cloud function test console. Confirm the returned counters and inspect `reminder_jobs`/`notification_logs` for `ready`, `skipped`, or `cancelled` states.
3. Run the scan repeatedly. The same `itemId + activeExpiryDate + reminderKind` must not create a second ready job.
4. Delete an item, mark it done, turn off reminders, or change its active expiry. Run the scan again and confirm the old ready job becomes `cancelled`.
5. Invoke `sendReminderNotifications` while dry-run is true. It must report `dryRun: true`, leave jobs unsent, and call no WeChat send API.

## Real-send cutover

Only after the dry-run evidence and template field verification are complete:

1. Set `REMINDER_DRY_RUN=false` on `sendReminderNotifications` only. The scanner may remain `true`; that flag is a safety default and does not send messages.
2. Deploy/restart the sender (and scanner if its configuration changed).
3. Use one test account and one eligible item.
4. Confirm exactly one `sent` job and one safe `notification_logs` record.
5. Test authorization unavailable (`43101`), capability/template ban (`43107`), invalid recipient (`40003`), invalid template (`40037`), field format (`47003`), and transient network failure. Confirm skipped/failed states and bounded retries. A `43101` or successful send consumes the current one-time authorization; the user must authorize again before another message can be sent.

If any verification fails, set `REMINDER_DRY_RUN=true` again. Do not manually edit job status to claim a send succeeded.
