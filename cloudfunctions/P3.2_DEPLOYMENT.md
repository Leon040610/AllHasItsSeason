# P3.2 一次性订阅消息部署与真机验证

## 能力边界

本项目使用普通一次性订阅消息，不使用也不模拟长期订阅消息。每次前端得到微信 API 的 `accept`，只为当次保存的一个物品创建一条可消费授权记录；云端最多向该物品发送一条到期提醒。

用户勾选“总是保持以上选择，不再询问”后，后续调用可能不再显示原生授权面板，而是直接返回原有的 `accept` 或 `reject`。这属于微信的正常行为，不代表长期订阅。是否真的可发送，必须以云端发送结果为准。

## 云函数与集合

部署以下三个云函数的全部文件：

- `registerReminderRecipient`：从微信上下文取得当前身份，更新加密接收端，并创建当前物品专属的 `notification_grants` 记录。
- `scheduledReminderScan`：按 `Asia/Shanghai` 检查物品和 grant，仅创建当前授权物品的提醒任务。
- `sendReminderNotifications`：认领一个任务及其 grant，调用微信订阅消息发送接口，并记录最终安全状态。

在云开发数据库创建下列集合，并设置为仅云函数可读写：

- `notification_recipients`：每个账号一条加密接收端记录，不代表可发送额度。
- `notification_grants`：每次 `accept` 一条额度记录，状态为 `available`、`sending`、`consumed`、`unavailable`、`cancelled` 或 `failed`。
- `reminder_jobs`：待发送任务；旧版没有 `grantId` 的 `ready` 任务将被安全取消，不会发送。
- `notification_logs`：仅保存任务、状态、有限重试次数和安全错误码。

不要在这些集合写入明文身份、模板 ID、密钥、完整错误响应、图片数据或本地路径。

## 环境变量

所有值都只在微信开发者工具的云开发环境变量中配置，绝不写入 `env.js`、代码、日志或聊天记录。

`registerReminderRecipient`：

```text
OWNER_KEY_SALT=<现有服务端值>
REMINDER_RECIPIENT_ENCRYPTION_KEY=<随机服务端密钥>
```

`scheduledReminderScan`：

```text
OWNER_KEY_SALT=<现有服务端值>
REMINDER_DRY_RUN=true
REMINDER_TEMPLATE_ID=<公众平台配置的模板 ID>
REMINDER_TEMPLATE_FIELDS=<当前模板的字段映射 JSON>
REMINDER_TIMEZONE=Asia/Shanghai
REMINDER_MAX_RETRIES=2
```

`sendReminderNotifications`：

```text
REMINDER_RECIPIENT_ENCRYPTION_KEY=<与 registerReminderRecipient 完全相同的值>
REMINDER_DRY_RUN=true
REMINDER_TEMPLATE_ID=<公众平台配置的模板 ID>
REMINDER_TEMPLATE_FIELDS=<当前模板的字段映射 JSON>
REMINDER_TIMEZONE=Asia/Shanghai
REMINDER_MAX_RETRIES=2
REMINDER_MINIPROGRAM_STATE=trial
```

`REMINDER_TEMPLATE_FIELDS` 必须是单行、可解析的 JSON。键名是固定业务名，值是当前订阅模板详情页中的字段名。当前已核对的模板字段可按以下格式配置；不要加入模板 ID、用户身份或任何密钥：

```json
{"itemName":"thing5","productionDate":"time8","daysLeft":"number2","expiryDate":"date1","note":"thing3"}
```

如果后续更换订阅模板，必须先按新模板详情页逐项更新这五个字段，再部署 `scheduledReminderScan` 与 `sendReminderNotifications`。字段名、字段类型或长度不匹配时，发送函数会记录安全错误码并停止当前任务，不会把消息伪装成已发送。

数据库集合建议使用以下非唯一索引，避免定时扫描在数据增长后因查询效率下降而超时。字段顺序不可颠倒：

- `items`：`idx_owner_item_id`，字段为 `ownerKey`、`id`。不要替代或删除历史的 `ownerKey`、`_id` 索引。
- `reminder_settings`：`idx_reminder_settings_owner`，字段为 `ownerKey`。
- `notification_recipients`：`idx_recipient_owner_status`，字段为 `ownerKey`、`status`。
- `notification_grants`：`idx_grant_owner_item_expiry_kind_status`，字段为 `ownerKey`、`itemId`、`activeExpiryDate`、`reminderKind`、`status`；另建 `idx_grant_owner_id`，字段为 `ownerKey`、`id`。
- `reminder_jobs`：`idx_job_owner_status`，字段为 `ownerKey`、`status`；另建 `idx_job_dedupe_key`，字段为 `dedupeKey`。
- `notification_logs`：`idx_log_job_id`，字段为 `jobId`。

所有四个集合都应禁止客户端直接读写，只保留云函数服务端访问。不要删除已有历史集合或历史记录。

体验版测试使用 `trial`。只有体验账号真实收到消息并在日志中出现 `sent` 后，正式版本才改为 `formal`。

如果此前截图暴露过接收端加密密钥，请生成新随机值，同时替换 `registerReminderRecipient` 与 `sendReminderNotifications` 的该变量，重新部署后让测试账号重新授权。不要单独轮换 `OWNER_KEY_SALT`，它与既有账号归属数据相关。

## 真实发送前的云调用权限修复

`sendReminderNotifications` 使用微信云调用 `cloud.openapi.subscribeMessage.send(...)`。因此该函数目录中的 `config.json` 必须同时保留定时触发器，并声明下列权限：

```json
{
  "permissions": {
    "openapi": ["subscribeMessage.send"]
  },
  "triggers": [
    {
      "name": "reminderSendAfterScan",
      "type": "timer",
      "config": "0 2/10 * * * * *"
    }
  ]
}
```

只需为 `sendReminderNotifications` 声明该权限；`scheduledReminderScan` 不调用发送接口，不需要声明 `subscribeMessage.send`。

部署时先右键 `sendReminderNotifications`，选择“上传并部署：所有文件”，使云端更新函数代码和 `permissions.openapi`。随后再次右键同一函数，选择“上传触发器”，保留 `reminderSendAfterScan` 的定时计划。微信云调用权限变更可能有缓存，最长等待约 10 分钟后再进行真实发送验证。

若 `notification_logs.errorCode` 为 `cloud_api_permission_missing`，且 `platformErrorCode` 为 `-604101`，表示云调用权限尚未声明、最新 `config.json` 尚未部署，或权限缓存尚未生效。它不是用户拒绝订阅：当前 grant 会保留为 `available`，修复权限后可由下一次扫描重新建立可处理任务。只有平台明确返回 `43101` 时，系统才会把当前一次性 grant 标记为 `unavailable` 并跳过该任务。

若 `notification_logs.platformErrorCode` 为 `-501007`，官方定义为云资源通用参数错误。发送函数会将任务记录为 `cloud_parameter_invalid`，但保持 grant 为 `available`。它不会盲目重试或消耗订阅机会。请先核对新测试物品已填写生产日期：当前 `time8` 必须发送为 `YYYY-MM-DD HH:mm`，`date1` 发送为 `YYYY-MM-DD`。该结论以真实云调用结果为准，模板详情页的静态预览不等同于接口参数校验规则。修正物品数据或部署本次参数格式修复后，再运行扫描函数即可重新建立 `ready` 任务。

此前因权限问题被错误标记为 `unavailable` 的旧 grant 不应复用。完成部署和等待后，必须新建一件测试物品，并重新完成一次订阅授权，再进行真实发送验证。

## 触发器与验证

定时触发器通过函数目录内的 `config.json` 声明，不是在数据库或环境变量页面手动新建。两个文件已随代码提供：

- `scheduledReminderScan/config.json`：`0 */10 * * * * *`，每十分钟的第 0 分钟扫描一次。
- `sendReminderNotifications/config.json`：`0 2/10 * * * * *`，每十分钟的第 2 分钟发送一次，位于对应扫描后的约两分钟。

Cron 表达式共七段，顺序为“秒、分钟、小时、日、月、星期、年”，微信定时触发器时区为 UTC+8。每个函数目录目前只能声明一个触发器。

部署顺序：先右键函数选择“上传并部署：所有文件”，再分别右键 `scheduledReminderScan` 和 `sendReminderNotifications` 选择“上传触发器”。确认开发者工具显示上传成功后，才会在云端按上述时间自动运行。需要暂停自动运行时，分别右键函数选择“删除触发器”；不要删除 `config.json` 或云函数源码。

1. 首先保持两个函数的 `REMINDER_DRY_RUN=true`。登录体验账号，新建一件满足提醒窗口的测试物品，点击保存并完成订阅调用。
2. 手动运行扫描函数。确认当前物品有一条 `notification_grants.status=available` 和一条带相同 `grantId` 的 `reminder_jobs.status=ready`。
3. 再次运行扫描函数，确认不产生重复任务。修改日期、关闭提醒、标记用完或删除物品，再运行扫描，确认旧任务和 grant 被取消或跳过。
4. dry-run 下运行发送函数，返回必须为 `dryRun: true`，不得发送微信消息、不得消费 grant。
5. 真机发送前，只将 `sendReminderNotifications` 的 `REMINDER_DRY_RUN` 改为 `false`，重新部署该函数。扫描函数可继续保留 dry-run 标识，因为它不会调用发送接口。
6. 用一件新的测试物品和一次新的授权记录手动运行扫描、再运行发送函数。成功标准是同一 grant 为 `consumed`、同一 job 为 `sent`、`notification_logs.status=sent`，且体验账号在微信服务通知中收到一条消息。

`authorization_unavailable` 或微信平台 `43101` 只表示当前一次性授权不能发送：系统会让当前 grant 失效并跳过当前任务，不会关闭该用户后续物品的提醒能力。新建或重新设置另一件提醒物品并再次调用订阅 API，才会获得新的测试机会。
