# P3.3 云文件与已删除数据治理部署说明

## 上线后的每周自动治理

本章是 P3.3 的自动化版本。它不需要你再从云存储控制台逐个复制文件清单，也不会通过小程序页面提供云端删除入口。

自动管理只覆盖本次版本部署成功以后新登记的文件。此前已经存在、但没有写入 `cloud_file_registry` 的历史文件会被保守保留，不会进入自动删除候选。这样可以避免首次上线时误删历史图片。

### 每周执行顺序

三个定时触发器都在每周日凌晨运行，按以下顺序错开二十分钟：

| 时间（北京时间） | 云函数 | 作用 |
| --- | --- | --- |
| 02:00 | `auditCloudFiles` | 读取未来上传文件的私有登记表，重新检查业务引用，生成文件候选与日志。 |
| 02:20 | `cleanupCloudFiles` | 再次检查候选后，默认只写 dry-run 日志；只有删除开关全部开启时才删除云文件。 |
| 02:40 | `purgeDeletedData` | 盘点已软删除满 7 天的 `items`，默认只写 dry-run 日志；满足全部开关时才物理清理 item 及明确关联的终态记录。 |

草稿箱不参与七天物理删除。任何草稿中引用的 Cloud File ID 均持续作为有效引用受到保护。

### 新增集合与索引

除本说明原有集合外，创建一个私有集合：

```text
cloud_file_registry
```

权限选择“所有用户不可读写”。它只由云函数写入和读取，字段包含 Cloud File ID、受控云路径、登记时间、来源类别及服务端归属摘要；小程序页面不读取它。

在“数据库 -> 索引”中创建：

| 集合 | 索引名称 | 字段（升序） | 用途 |
| --- | --- | --- | --- |
| `cloud_file_registry` | `idx_file_registry_createdAt` | `createdAt` | 周期盘点与保留期统计。 |
| `cleanup_logs` | `idx_cleanup_logs_operation_createdAt` | `operation`, `createdAt` | 文件清理函数定位最近一次自动盘点。 |

### 每个函数的环境变量

所有变量都在对应云函数详情的“环境变量”页面配置，不能写进 `env.js`、前端代码或数据库。`CLEANUP_ADMIN_TOKEN` 必须在以下三个函数使用同一个新随机值：`auditCloudFiles`、`cleanupCloudFiles`、`purgeDeletedData`。此前曾暴露过的旧值不要继续使用。

`registerCloudFile`：

```text
OWNER_KEY_SALT=<与 login、syncData 使用的同一服务端盐值>
```

`auditCloudFiles`：

```text
CLEANUP_ADMIN_TOKEN=<新的随机维护口令>
CLOUD_FILE_RETENTION_DAYS=7
CLEANUP_AUTO_AUDIT_ENABLED=true
CLEANUP_DRY_RUN=true
CLEANUP_DELETE_ENABLED=false
```

`cleanupCloudFiles`：

```text
CLEANUP_ADMIN_TOKEN=<同一个新的随机维护口令>
CLOUD_FILE_RETENTION_DAYS=7
CLEANUP_DRY_RUN=true
CLEANUP_DELETE_ENABLED=false
CLEANUP_AUTO_DELETE_ENABLED=false
CLEANUP_AUTO_DELETE_LIMIT=10
```

`purgeDeletedData`：

```text
CLEANUP_ADMIN_TOKEN=<同一个新的随机维护口令>
DELETED_RECORD_RETENTION_DAYS=7
RECORD_PURGE_AUTO_AUDIT_ENABLED=true
RECORD_PURGE_DRY_RUN=true
RECORD_PURGE_DELETE_ENABLED=false
RECORD_PURGE_AUTO_DELETE_ENABLED=false
RECORD_PURGE_AUTO_DELETE_LIMIT=10
```

含义：`*_AUTO_AUDIT_ENABLED=true` 只允许定时盘点；删除仍需要对应的 `*_DRY_RUN=false`、`*_DELETE_ENABLED=true`、`*_AUTO_DELETE_ENABLED=true` 三项同时成立。任何一项不是该值，定时函数只会记录 dry-run 或跳过，不会调用云文件删除或数据库 `remove()`。

### 首次部署与自动 dry-run

1. 在同一云开发环境创建 `cloud_file_registry` 及上述两个索引，等待状态显示“已生效”。
2. 在开发者工具中依次右键并执行“上传并部署：所有文件”：

```text
cloudfunctions/registerCloudFile
cloudfunctions/imageProcess
cloudfunctions/auditCloudFiles
cloudfunctions/cleanupCloudFiles
cloudfunctions/purgeDeletedData
cloudfunctions/syncData
```

3. 再分别右键 `auditCloudFiles`、`cleanupCloudFiles`、`purgeDeletedData`，执行“上传触发器”。只有这一步才会把目录中的 `config.json` 每周计划写入 CloudBase。
4. 保持上表所有删除开关为默认值，先用已登录真机新建一件带图片的物品。确认 `cloud_file_registry` 增加一条对应登记记录，`items` 的 Cloud File ID 正常存在。
5. 不必等到周日：可在云函数控制台运行测试。自动盘点使用空事件 `{}`；自动清理与自动数据清理也使用空事件 `{}`。在删除开关为默认值时，它们只会产生 `cleanup_logs` 安全摘要，不删除任何文件或 item。
6. 观察 `cleanup_logs`：应先有 `audit_auto`，后有 `file_cleanup_auto`、`data_purge_auto`。没有超过七天的候选时，候选数量为零是正确结果。

### 真正开启每周自动删除

现在没有超过七天的数据时，不应直接把删除开关全部开启。先让至少一个明确的测试候选自然超过 7 天，确认 dry-run 候选与业务实际一致，并在控制台导出 `items`、`image_jobs`、`reminder_jobs`、`notification_grants`、`notification_logs`、`cleanup_candidates`、`purge_candidates`、`cleanup_logs` 做备份。

之后按独立功能分别开启，且每次只改一个函数：

文件孤儿清理（仅 `cleanupCloudFiles`）：

```text
CLEANUP_DRY_RUN=false
CLEANUP_DELETE_ENABLED=true
CLEANUP_AUTO_DELETE_ENABLED=true
```

7 天以上已删除 item 物理清理（仅 `purgeDeletedData`）：

```text
RECORD_PURGE_DRY_RUN=false
RECORD_PURGE_DELETE_ENABLED=true
RECORD_PURGE_AUTO_DELETE_ENABLED=true
```

每次变更环境变量后，重新执行该函数的“上传并部署：所有文件”。保留 `CLEANUP_AUTO_DELETE_LIMIT=10`、`RECORD_PURGE_AUTO_DELETE_LIMIT=10`，即每周每类最多处理 10 条；不要提高到无上限。

如需立即停用真实自动删除，只需将这两个函数的 `*_AUTO_DELETE_ENABLED` 改回 `false`，然后重新部署对应函数。定时盘点仍可继续运行，不会删除内容。


本阶段的默认状态是盘点和演练。它不会自动删除云存储文件，也不会自动删除云数据库记录。请先完成全部 dry-run 验证，再单独确认是否允许极小批次的真实删除。

实现已按两份官方文档核对：云函数侧数据库单文档物理删除使用 `doc(...).remove()`；云存储删除使用 `wx-server-sdk` 的 `cloud.deleteFile({ fileList })`，且仅当返回项 `status` 为数值 `0` 时才记录成功。你提供的 [删除数据官方文档](https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloud/guide/database/remove.html) 与 [删除云存储文件官方文档](https://developers.weixin.qq.com/miniprogram/dev/server/API/cloudbase/storage/api_deletetcbcloudfile.html) 中的 HTTPS `deleteTcbCloudFile` 面向外部服务端，不能替换为 `cloud.openapi` 云调用；本项目不会在前端直接调用任一删除接口。

## 一、四个云函数

请在微信开发者工具中分别右键以下目录，执行“上传并部署：所有文件”。本阶段不上传触发器，也不配置自动清理触发器。

```text
cloudfunctions/auditCloudFiles
cloudfunctions/cleanupCloudFiles
cloudfunctions/purgeDeletedData
cloudfunctions/syncData
```

`syncData` 的部署用于让旧设备在完整墓碑被清除后，仍能收到最小删除标记，避免旧物品或旧草稿重新写回云端。

## 二、创建集合

在同一个云开发环境创建以下空集合。集合权限保持为仅云函数可读写；小程序前端不需要、也不应直接访问这些集合。

```text
cloud_file_inventory
cleanup_candidates
cleanup_logs
sync_tombstones
purge_candidates
```

字段说明：

| 集合 | 用途 | 会保存的内容 |
| --- | --- | --- |
| `cloud_file_inventory` | 一次文件盘点的输入清单 | 文件 ID、受控目录路径、大小、创建时间和快照 ID |
| `cleanup_candidates` | 文件盘点结果 | 仅候选状态、原因码和安全摘要 |
| `cleanup_logs` | 文件与数据治理操作日志 | 数量、状态、原因码、哈希化引用，不含文件 ID 明文 |
| `sync_tombstones` | 长期防复活索引 | `ownerKey`、集合名、记录 ID、删除时间、物理清理时间 |
| `purge_candidates` | 已删除业务记录的 7 天审计结果 | 运行 ID、记录类型、候选状态和原因码 |

`sync_tombstones` 不是完整商品备份，不保存商品名称、日期、备注、图片、时间线、openid 或本地路径。P3.3 只会为被物理清理的 item 写入这类记录；它必须长期保留，不能在 7 天后一起清除。

## 三、建议索引

在云开发控制台的“数据库 -> 索引”中按下表创建。字段全部使用升序。若控制台提示内置 `_id` 已自动建立，不需要重复建立 `_id` 单字段索引。

| 集合 | 索引名称 | 字段（升序） | 用途 |
| --- | --- | --- | --- |
| `items` | `idx_items_status_deletedAt` | `status`, `deletedAt` | 查找已删除且超过保留期的物品 |
| `sync_tombstones` | `idx_tombstones_ownerKey` | `ownerKey` | 按当前账号拉取防复活标记 |
| `image_jobs` | `idx_image_jobs_ownerKey_itemId` | `ownerKey`, `itemId` | 清理前复查关联图片任务 |
| `notification_grants` | `idx_grants_ownerKey_itemId` | `ownerKey`, `itemId` | 清理关联的一次性订阅授权 |
| `reminder_jobs` | `idx_reminder_jobs_ownerKey_itemId` | `ownerKey`, `itemId` | 清理前复查、清理关联提醒任务 |
| `notification_logs` | `idx_notification_logs_jobId` | `jobId` | 删除已清理提醒任务的安全日志 |
| `cloud_file_inventory` | `idx_inventory_snapshotId` | `snapshotId` | 读取一次盘点输入 |
| `cleanup_candidates` | `idx_cleanup_snapshot_status` | `snapshotId`, `status` | 读取本次 `ready` 文件候选 |
| `purge_candidates` | `idx_purge_run_status` | `runId`, `status` | 读取本次 `ready` 数据候选 |

索引创建完成后等待控制台显示“已生效”，再进行 dry-run。若已有相同字段顺序的索引，不需要重复创建。

## 四、环境变量

所有变量都在云函数详情页的“环境变量”中配置。`CLEANUP_ADMIN_TOKEN` 是维护口令，使用一段新的高强度随机文本；不要放进 `env.js`、代码、截图、数据库记录或小程序页面。

### `auditCloudFiles`

```text
CLEANUP_ADMIN_TOKEN=仅由开发者保管的随机维护口令
CLOUD_FILE_RETENTION_DAYS=7
CLEANUP_DRY_RUN=true
CLEANUP_DELETE_ENABLED=false
```

该函数无论配置如何都不会调用云存储删除接口。后两个变量保持与本阶段统一的默认安全态一致。

### `cleanupCloudFiles`

```text
CLEANUP_ADMIN_TOKEN=与 auditCloudFiles 完全相同的维护口令
CLOUD_FILE_RETENTION_DAYS=7
CLEANUP_DRY_RUN=true
CLEANUP_DELETE_ENABLED=false
```

只有同时满足 `CLEANUP_DRY_RUN=false` 与 `CLEANUP_DELETE_ENABLED=true` 时，函数才会调用云存储删除接口。任一变量不是该值，函数只写 dry-run 日志。

### `purgeDeletedData`

```text
CLEANUP_ADMIN_TOKEN=与上述两个函数完全相同的维护口令
DELETED_RECORD_RETENTION_DAYS=7
RECORD_PURGE_DRY_RUN=true
RECORD_PURGE_DELETE_ENABLED=false
```

只有同时满足 `RECORD_PURGE_DRY_RUN=false` 与 `RECORD_PURGE_DELETE_ENABLED=true` 时，函数才会物理删除已超过 7 天的完整 `items` 文档及其明确关联数据。草稿箱中的草稿不参与此流程，会一直保留。

所有保留期均固定为 `7`。设置为其他数值会让函数以 `retention_config_invalid` 或 `record_retention_config_invalid` 停止，不会删除任何内容。

## 五、首次文件盘点 dry-run

当前 CloudBase Node SDK 没有可靠的“列举整个存储桶”接口可供本项目安全使用。因此 `auditCloudFiles` 使用控制台清单导入模式，不会假装已经扫描全桶。

1. 在云存储控制台分别筛选并导出或手工整理以下受控目录的文件清单：`uploads/`、`processed/`、`avatars/`。
2. 不要加入字体、公共资源或其他目录。每条只保留控制台能核实的四个字段：`fileId`、`cloudPath`、`sizeBytes`、`createdAt`（毫秒时间戳）。无法确认创建时间、路径或 File ID 的文件不要导入。
3. 在 `auditCloudFiles` 的“云端测试”运行以下事件，保存返回的 `snapshotId`：

```json
{
  "action": "beginSnapshot",
  "adminToken": "<仅在此处临时填写维护口令>"
}
```

4. 使用该 `snapshotId`，每次最多导入 100 个文件。以下只是字段格式示例，不能照抄占位值：

```json
{
  "action": "appendInventory",
  "adminToken": "<维护口令>",
  "snapshotId": "<步骤 3 返回的 snapshotId>",
  "files": [
    {
      "fileId": "cloud://<当前环境>/<受控文件 ID>",
      "cloudPath": "uploads/<图片任务 ID>/original.jpg",
      "sizeBytes": 12345,
      "createdAt": 1700000000000
    }
  ]
}
```

5. 全部批次导入完成后运行审计：

```json
{
  "action": "runAudit",
  "adminToken": "<维护口令>",
  "snapshotId": "<步骤 3 返回的 snapshotId>"
}
```

6. 在 `cleanup_candidates` 中只检查该 `snapshotId`。`ready` 的含义是“在导入清单中、路径受控、超过 7 天、没有当前业务引用、没有进行中的图片任务保护”。这仍不是删除命令。

## 六、7 天数据保留 dry-run

在 `purgeDeletedData` 的“云端测试”运行：

```json
{
  "action": "audit",
  "adminToken": "<维护口令>"
}
```

返回的 `runId` 对应一次仅审计的结果。检查 `purge_candidates`：

- `ready`：已软删除至少 7 天的物品，并且没有 `idle` 或 `cutting` 图片任务，也没有 `sending` 提醒任务；
- `skipped`：仍在保留期、图片任务进行中、提醒正在发送或关键归属信息不完整；
- `failed`：仅会在真实执行阶段出现，需先查 `cleanup_logs` 的安全原因码。

dry-run 不会改变 `items`、草稿、图片文件或关联提醒数据。草稿不进入候选集合，也不会因保留时长而被清理。

## 七、真实删除前的人工确认

不要直接切换全部删除。完成 dry-run 并人工核对后，按照下面的最小批次顺序执行：

1. 备份 `items`、`drafts`、`image_jobs`、`notification_grants`、`reminder_jobs`、`notification_logs`、`cleanup_candidates`、`purge_candidates` 和 `cleanup_logs`。
2. 从 `cleanup_candidates` 或 `purge_candidates` 任选一条明确的测试候选，确认它不属于仍在使用的物品、草稿、头像或进行中的图片任务。
3. 仅修改要验证的一个函数开关，并重新部署该函数的所有文件。
4. 对文件候选，先把 `cleanupCloudFiles` 设置为 `CLEANUP_DRY_RUN=false` 与 `CLEANUP_DELETE_ENABLED=true`，再用 `maxDeletes: 1` 手动运行。对数据候选，先把 `purgeDeletedData` 设置为 `RECORD_PURGE_DRY_RUN=false` 与 `RECORD_PURGE_DELETE_ENABLED=true`，再用 `maxRecords: 1` 手动运行。数据清理始终先写 `sync_tombstones`，再调用官方支持的 `doc(...).remove()`；前一步成功而后一步失败时，完整记录会继续保留为软删除状态，下一次手动执行可安全重试。
5. 立即在 `cleanup_logs` 中核对 `deleted`、`skipped` 或 `failed`，并在两台设备上同步确认没有现有物品破图或复活。`failed` 候选不会被丢弃，下一次同一快照或同一运行 ID 的手动执行会重新做安全复查后重试。
6. 将刚刚开启的两个开关恢复为默认 dry-run 值，并重新部署该函数。

文件清理事件格式：

```json
{
  "adminToken": "<维护口令>",
  "snapshotId": "<已核对的 snapshotId>",
  "maxDeletes": 1
}
```

数据清理事件格式：

```json
{
  "action": "execute",
  "adminToken": "<维护口令>",
  "runId": "<已核对的 runId>",
  "maxRecords": 1
}
```

## 八、明确不会发生的事

- 不会通过“清理本地缓存”按钮删除云端文件；
- 不会自动删除未满 7 天的软删除物品或图片；草稿箱中的草稿始终保留；
- 不会删除用户级 `notification_recipients`、`reminder_settings`、`sync_settings`、`users`、`categories` 或 `recognition_logs`；
- 不会自动部署云函数、创建集合、创建索引、启用触发器或执行真实删除；
- 不会让已物理清理的旧 item 因旧设备同步而重新创建，`sync_tombstones` 会阻止这类上行。
